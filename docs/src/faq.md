# Frequently asked questions

Short answers to common questions. Each answer links to the page with the
details.

## Does DrakeFlake change my own .nix files?

No. The app only writes its own generated files, by default `drakeflake.nix`
next to your `flake.nix`. Your host configuration imports that file once.

Every generated file starts with the header
`# GENERATED by DrakeFlake - safe to delete.`. The app only overwrites or
removes `.nix` files inside a flake that carry this header or are empty. A file
without the header is never replaced. See
[What it changes](introduction.md#what-it-changes).

## What does it write, and where?

Inside your system flake it writes the generated files and, when you update
inputs, `flake.lock`. Everything else stays in your home folder:

- settings in `~/.config/drakeflake/config.toml`,
- logs, backups and staged changes in `~/.local/state/drakeflake/`,
- caches in `~/.cache/drakeflake/`.

With a split layout the generated files are in a `drakeflake/` folder next to
`flake.nix`. To read them before they are written, click **Preview file** on
the **Changes** page. See
[Where things are](troubleshooting.md#where-things-are) and
[Privacy and security](security.md).

## Does it commit or push my flake?

It commits, but it never pushes. With **Commit the changes on apply** on (the
default), every successful apply commits all changes in the flake folder with
the subject `drakeflake: update config`.

Nothing is committed when the rebuild fails. A flake without a git repository
gets one first. To commit yourself, switch the setting off in
[Settings](settings.md#applying). See
[Automatic commits](applying.md#automatic-commits).

## How do I undo a change?

It depends on how far the change got:

- **Staged, not applied:** click the undo button at the end of its row on the
  **Changes** page. **Discard all** drops every staged change.
- **Applied:** open the **History** page, click **Restore** on an earlier
  state, then apply again. The current settings stay in the history.
- **After a failed apply:** click **Restore previous file** in the
  **Console**.
- **Go back to an earlier system:** use **Switch to** on the **Generations**
  page.
- **Undo everything the app did:** delete the generated files and remove their
  import from your host configuration, then rebuild.

> **Warning:** **Discard all** drops every staged change at once, without
> asking first. There is no button to get them back.

See [History and restoring](applying.md#history-and-restoring) and
[Generations](maintenance.md#generations).

## Does it need root, and when?

Only for a few steps, and it asks for your password for them. Almost
everything else runs as your user, for example searching, evaluating and
updating inputs.

Root is needed to activate a built system, to write generated files into a
flake you cannot write to (for example a root-owned `/etc/nixos`) and to save
an updated `flake.lock` there. On NixOS the password prompt is your desktop's
polkit dialog. On a Mac it is the macOS administrator dialog. See
[Privacy and security](security.md).

## Does it work on macOS with nix-darwin?

Yes, on Apple silicon. Pick a flake with `darwinConfigurations`, and the app
builds with `nh darwin build` and activates under one administrator dialog.
Without nh it runs `darwin-rebuild switch` as root.

Image building and the Test and Boot modes are left out, because nix-darwin
has no equivalent. Intel Macs are not supported. See
[nix-darwin systems](darwin.md).

## Can I edit a nix-darwin host from Linux, or a NixOS host from a Mac?

Yes, but you can only save it. A host can only be built and activated on the
kind of system it describes. The **Changes** page then offers **Save only**.
Copy or push the flake to the other machine and apply it there. See
[Hosts of the other platform](darwin.md#hosts-of-the-other-platform).

## Does it work with Home Manager?

Yes, when Home Manager is imported as a system module
(`home-manager.nixosModules.home-manager` on NixOS,
`home-manager.darwinModules.home-manager` on nix-darwin) and your user is set
up in `home-manager.users.<name>`. A standalone Home Manager setup with its own
`home-manager switch` is not managed by the app.

Home Manager settings go into the same generated files and are applied with
the next system rebuild. See [Home Manager](home-manager.md).

## Do I need nh?

No, but it is recommended. Without nh the app builds with `nixos-rebuild`,
switches generations through its own helper and cleans up with
`nix-collect-garbage`.

**Review and apply…** needs nh. Without it the files are saved and the
Console says to use **Apply** instead. The **Actions** page recommends
installing nh when it is missing. See
[Installation and requirements](installation.md).

## What happens if the build fails?

Your running system is not changed, and nothing is committed to git. The
**Console** shows the output, and its last lines usually name the problem.

Click **Restore previous file** to put the generated file back as it was
before the apply. See [Applying failed](troubleshooting.md#applying-failed).

## Why is the first start so slow?

The first start builds and caches the option, value and package indexes in
`~/.cache/drakeflake/`. Later starts reuse them and evaluate only what changed.
See [The first start is slow](troubleshooting.md#the-first-start-is-slow).
